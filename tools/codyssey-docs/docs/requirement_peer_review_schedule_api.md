# Codyssey 캘린더 API 조사 및 일정 유형별 조회 검증 요구사항 명세서

## 1. 프로젝트 개요

### 1.1 목적

Codyssey 사용자 사이트에 표시되는 캘린더 일정을 외부 캘린더 서비스와 연동하기 위한 사전 조사 작업이다.

최종 목표는 Codyssey 캘린더의 일정을 Google Calendar에 직접 등록하고, 이후 Codyssey에서 일정이 변경되거나 취소되었을 때 Google Calendar에도 반영하는 프로그램을 개발하는 것이다.

본 문서는 해당 프로그램 개발에 앞서 Codyssey의 실제 일정 조회 API를 조사하고, 캘린더에 표시되는 모든 종류의 일정이 API를 통해 조회 가능한지 검증하는 것을 목적으로 한다.

이 문서만 전달받은 에이전트도 이전 대화나 별도 설명 없이 조사를 진행할 수 있어야 한다.

### 1.2 핵심 검증 대상

다음 일정 유형이 API 응답에 포함되는지 반드시 확인한다.

1. 평가 요청 일정
2. 평가 참여 일정
3. 전문가 평가 일정
4. 전문가 특강 일정
5. 그 밖에 Codyssey 캘린더에 표시되는 일정

단순히 API가 정상 응답을 반환하는지만 확인해서는 안 된다. 실제 웹 화면에 표시되는 일정과 API 응답을 대조하여 일정 유형별 누락 여부를 검증해야 한다.

## 2. 현재까지 확인된 정보

### 2.1 Codyssey 관련 사이트

| 구분 | URL |
|---|---|
| Codyssey 메인 | https://usr.codyssey.kr/main |
| 평가 일정 | https://usr.codyssey.kr/ev/schedule/evaluationScheduleList |
| 평가 요청 | https://usr.codyssey.kr/ev/request/evalutionRequestList |
| 평가 참여 | https://usr.codyssey.kr/ev/participation/evalutionParticipationList |
| 공식 소개 | https://ams.codyssey.kr/about/intro |
| AI Native 과정 안내 | https://codyssey.kr/guide/aiNative |

Codyssey 사용자 사이트는 로그인이 필요한 서비스다.

따라서 실제 API 테스트는 정상적으로 로그인한 사용자의 브라우저 세션을 이용해야 한다.

### 2.2 기존에 발견한 API

공개 GitHub 저장소에서 Codyssey API를 호출하는 코드를 발견했다.

**API 주소**

```http
POST https://usr.codyssey.kr/schedule/scheduleAllList/
```

**확인된 요청 파라미터**

| 파라미터 | 확인된 값 | 설명 |
|---|---|---|
| bgngYmd | 날짜 문자열 | 조회 시작일 |
| endYmd | 날짜 문자열 | 조회 종료일 |
| scheculeType | request | 일정 유형 관련 파라미터 |
| searchType | T | 검색 유형 관련 파라미터 |

주의: `scheculeType`은 철자가 잘못된 것처럼 보이지만 공개 소스코드에 등장하는 실제 파라미터 표기다. 임의로 `scheduleType`으로 수정하지 않는다.

**공개 소스에서 확인된 응답 접근 방식**

```javascript
fetch(url, {
    method: 'POST',
    body: formData
})
.then(response => response.json())
.then(data => organizeTimeListByDate(data.result.timeList));
```

확인된 응답 데이터 경로:

```text
data.result.timeList
```

관련 필드:

- `bgngYmd`: 일정 날짜로 사용되는 필드
- `fixedNm`: 시간 구간으로 사용되는 필드
- `scdlId` 또는 `evlScdlSn`: 일정 식별자로 사용되는 것으로 보이나 실제 응답에서 확인 필요

**중요한 한계**

현재까지 확인한 공개 구현은 `scheculeType=request`를 사용하고 있어 평가 요청 가능 시간을 조회하는 용도일 가능성이 있다.

이 API가 평가 참여 일정이나 전문가 특강까지 반환한다는 증거는 아직 없다.

따라서 이 API 하나만으로 전체 캘린더를 구현할 수 있다고 가정해서는 안 된다.

## 4. 세부 요구사항

### REQ-001. 로그인 세션 확보

Codyssey 사용자 사이트에 정상적으로 로그인한 브라우저 환경을 확보한다.

- 로그인은 사용자가 직접 수행한다.
- 기존 브라우저 세션을 사용할 수 있다면 우선 활용한다.
- 인증 쿠키, 세션 토큰, 비밀번호를 외부에 노출하지 않는다.
- 로그인 세션을 우회하거나 인증을 무력화하지 않는다.

### REQ-002. 캘린더 화면 분석

다음 페이지를 조사한다.

```text
https://usr.codyssey.kr/ev/schedule/evaluationScheduleList
```

페이지에 표시되는 일정의 유형과 상세 정보를 확인한다.

확인할 항목:

- 일정 제목
- 일정 유형
- 시작 날짜 및 시간
- 종료 날짜 및 시간
- 장소 또는 온라인 여부
- 상세 정보
- 취소 여부
- 변경 여부
- 일정 상세 페이지 URL

특히 평가 참여 일정과 전문가 특강이 실제 캘린더에 표시되는지 확인한다.

일정이 표시되지 않는 경우에는 실제 일정이 없는 것인지, 조회 조건이나 화면 필터 때문에 보이지 않는 것인지 구분한다.

### REQ-003. 네트워크 요청 수집

브라우저 개발자 도구의 Network 탭을 활용한다.

1. Network 탭을 연다.
2. Fetch/XHR 필터를 적용한다.
3. Preserve log를 활성화한다.
4. 캘린더 페이지를 새로고침한다.
5. 일정이 로딩될 때 발생하는 요청을 확인한다.
6. 각 요청의 URL, HTTP Method, Request Payload, Response를 기록한다.

다음 사항을 특히 확인한다.

- `/schedule/` 경로를 사용하는 API
- `scheduleAllList` 관련 요청
- 평가 참여 관련 요청
- 전문가 특강 관련 요청
- 공통 일정 조회 요청
- 페이지 진입 시 호출되는 추가 API
- 월 이동 또는 날짜 변경 시 발생하는 요청

단순히 URL에 `schedule`이라는 문자열이 포함되어 있는지만으로 API를 판단하지 않는다.

### REQ-004. 평가 요청 일정 검증

다음 API를 우선 검증한다.

```http
POST https://usr.codyssey.kr/schedule/scheduleAllList/
```

기존에 확인된 파라미터를 사용하되, 실제 브라우저 요청과 비교한다.

```text
bgngYmd
endYmd
scheculeType=request
searchType=T
```

검증 항목:

- 응답이 정상적으로 반환되는가?
- `data.result.timeList`가 존재하는가?
- 평가 요청 가능 시간이 반환되는가?
- 평가 요청이 완료된 일정도 반환되는가?
- 일정 식별자가 존재하는가?
- 일정 제목과 날짜를 구분할 수 있는가?

### REQ-005. 평가 참여 일정 검증

평가 참여 메뉴를 조사한다.

```text
https://usr.codyssey.kr/ev/participation/evalutionParticipationList
```

평가 참여 화면에 표시되는 일정과 관련 API를 확인한다.

검증 항목:

- 참여 예정 평가가 반환되는가?
- 이미 참여한 평가도 반환되는가?
- 평가 일정과 평가 참여 기록이 구분되는가?
- 참여 상태가 응답에 포함되는가?
- 평가 시작 및 종료 시간이 존재하는가?
- 평가 취소 또는 변경 상태를 확인할 수 있는가?

평가 참여 화면에서만 사용하는 API가 발견되면 별도의 API로 기록한다.

### REQ-006. 전문가 특강 일정 검증

전문가 특강이 캘린더에 표시되는지 확인한다.

검증 항목:

- 특강 일정이 캘린더에 표시되는가?
- 기존 `scheduleAllList` API에서도 반환되는가?
- 별도의 특강 조회 API가 존재하는가?
- 특강 제목, 날짜, 시작 시간, 종료 시간이 반환되는가?
- 강사명, 장소, 신청 URL 등 부가 정보가 존재하는가?
- 신청 및 취소 상태를 확인할 수 있는가?

특강이 캘린더 화면에 표시되지만 기존 API에서 반환되지 않는다면, 별도의 API 호출 또는 추가 데이터 조회가 필요한 것으로 판단한다.

### REQ-007. 일정 유형별 API 분류

발견한 API를 일정 유형별로 정리한다.

| 일정 유형 | API 주소 | HTTP Method | 조회 가능 여부 | 비고 |
|---|---|---|---|---|
| 평가 요청 | 조사 필요 | 조사 필요 | 미검증 | 기존 API 후보 존재 |
| 평가 참여 | 조사 필요 | 조사 필요 | 미검증 | 별도 페이지 존재 |
| 전문가 평가 | 조사 필요 | 조사 필요 | 미검증 | 확인 필요 |
| 전문가 특강 | 조사 필요 | 조사 필요 | 미검증 | 확인 필요 |
| 기타 일정 | 조사 필요 | 조사 필요 | 미검증 | 추가 발견 시 기록 |

하나의 API가 여러 일정 유형을 반환하는 경우에도 유형별 구분이 가능한지 확인한다.

### REQ-008. 일정 변경 및 취소 검증

Google Calendar 동기화를 위해 일정의 변경 및 취소 여부를 확인할 수 있어야 한다.

검증 항목:

- 일정의 고유 식별자
- 일정 변경 시 식별자가 유지되는지 여부
- 일정 취소 시 응답에서 제거되는지 여부
- 취소 상태를 나타내는 필드 존재 여부
- 일정 삭제와 취소의 구분 가능 여부
- 과거 일정 조회 가능 여부

실제 일정을 임의로 취소하거나 변경하지 않는다.

가능하다면 기존 데이터와 현재 데이터를 비교하거나, 사용자가 확인 가능한 테스트 사례를 활용한다.

## 5. 테스트 방법

### 5.1 기본 테스트

기존에 발견한 API를 먼저 테스트한다.

조회 기간은 현재 날짜를 기준으로 과거와 미래를 모두 포함하도록 설정한다.

예시:

```text
bgngYmd=20261001
endYmd=20261231
```

날짜 형식은 실제 브라우저 요청에서 확인한 형식을 최종 기준으로 삼는다.

응답 JSON 전체를 확보하고 다음 사항을 확인한다.

- 최상위 JSON 구조
- `result` 객체 구조
- `timeList` 배열의 존재 여부
- 배열 원소별 필드
- 일정 식별자
- 날짜 및 시간
- 일정 유형을 구분할 수 있는 필드

### 5.2 일정 유형별 대조 테스트

API 응답만 보고 일정 유형을 추정하지 않는다.

다음과 같이 화면에 표시되는 실제 일정과 API 결과를 대조한다.

| 화면에서 확인한 일정 | API 응답에서 발견 | 동일 일정 판별 | 결과 |
|---|---|---|---|
| 평가 요청 | 확인 필요 | 확인 필요 | 미검증 |
| 평가 참여 | 확인 필요 | 확인 필요 | 미검증 |
| 전문가 평가 | 확인 필요 | 확인 필요 | 미검증 |
| 전문가 특강 | 확인 필요 | 확인 필요 | 미검증 |

일정 제목이 다르게 표현되거나 식별자가 다른 경우에도 날짜, 시간, 상세 정보를 이용하여 동일 일정인지 확인한다.

### 5.3 날짜 범위 테스트

다음 조건을 테스트한다.

- 하루 단위 조회
- 일주일 단위 조회
- 한 달 단위 조회
- 과거 일정 조회
- 미래 일정 조회

API가 특정 날짜 범위에서만 정상 작동하거나 최대 조회 기간 제한이 있는지도 확인한다.

### 5.4 파라미터 테스트

기존에 확인된 `scheculeType=request` 외에 다른 값이 존재하는지 조사한다.

단, 임의의 파라미터를 무차별적으로 대입하지 않는다.

우선순위는 다음과 같다.

1. 실제 웹 화면에서 발생하는 요청
2. 공개 GitHub 소스코드
3. 페이지에서 참조하는 JavaScript
4. 실제 요청과 응답을 근거로 한 제한적인 추가 검증

## 6. 결과물 요구사항

조사가 완료되면 다음 결과물을 작성한다.

### 6.1 API 명세서

파일명:

```text
codyssey-api-analysis.md
```

포함 내용:

- API 주소
- HTTP Method
- 인증 방식
- Request Headers
- Request Payload
- Response JSON 구조
- 필드별 의미
- 일정 식별자
- 일정 유형
- 날짜 및 시간 형식
- 오류 응답
- 조회 기간 제한
- 변경 및 취소 상태 확인 방법

확인하지 못한 항목은 추측하지 말고 `미확인`으로 표시한다.

### 6.2 테스트 결과서

파일명:

```text
codyssey-calendar-api-test.md
```

포함 내용:

- 테스트 환경
- 테스트 날짜
- 테스트한 화면 URL
- 호출한 API 목록
- 일정 유형별 조회 결과
- 실제 화면과 API 응답 대조 결과
- 누락된 일정 유형
- 추가 조사가 필요한 사항

### 6.3 원본 응답 데이터

가능하면 테스트에 사용한 응답 JSON을 별도로 저장한다.

예시:

```text
test-data/
├── schedule-request.json
├── evaluation-participation.json
├── expert-lecture.json
└── other-schedules.json
```

개인정보 및 인증정보는 제거하거나 익명화한다.

실제 데이터가 없는 경우에는 임의의 테스트 데이터를 실제 응답인 것처럼 작성하지 않는다.

## 7. 보안 및 작업 제약

- 사용자의 로그인 정보를 요청하거나 파일에 저장하지 않는다.
- 쿠키, 세션 ID, Authorization 토큰 등 인증정보를 결과물에 포함하지 않는다.
- 사용자가 접근할 권한이 있는 데이터만 조회한다.
- Codyssey 서버에 과도한 요청을 보내지 않는다.
- 불필요한 POST 요청이나 데이터 변경 요청을 실행하지 않는다.
- 실제 평가 요청, 평가 취소, 특강 신청 등 사용자 상태를 변경하는 작업은 수행하지 않는다.
- 응답 데이터에 개인정보가 있다면 결과물 작성 전에 익명화한다.

## 8. 완료 조건

다음 조건을 모두 충족해야 이번 조사 작업을 완료한 것으로 판단한다.

- [ ] 평가 일정 페이지의 네트워크 요청을 분석했다.
- [ ] 평가 요청 일정의 API를 확인했다.
- [ ] 평가 참여 일정의 API를 확인했다.
- [ ] 전문가 특강 일정의 API를 확인했다.
- [ ] 전문가 평가 등 기타 일정 유형을 확인했다.
- [ ] 일정 유형별 API 응답 포함 여부를 검증했다.
- [ ] 실제 화면에 표시되는 일정과 API 응답을 대조했다.
- [ ] 일정 고유 식별자를 확인했다.
- [ ] 변경 및 취소 상태를 확인할 수 있는지 조사했다.
- [ ] API 명세서와 테스트 결과서를 작성했다.

특정 일정 유형을 확인할 수 없는 경우에도 작업을 임의로 완료 처리하지 않는다. 해당 유형의 조회 실패 원인과 추가로 필요한 접근 방법을 기록한다.

## 9. 최종 조사 결과에 대한 핵심 질문

조사가 끝나면 다음 질문에 명확하게 답해야 한다.

1. `scheduleAllList` API 하나로 Codyssey 캘린더의 모든 일정을 가져올 수 있는가?
2. 평가 요청 일정과 평가 참여 일정은 동일 API에서 반환되는가?
3. 전문가 특강은 캘린더 조회 API에 포함되는가?
4. 일정 유형별로 별도의 API가 존재하는가?
5. 각 일정의 변경 및 취소 여부를 API만으로 확인할 수 있는가?
6. Google Calendar에 중복 없이 일정을 등록하고 변경·취소까지 동기화하려면 어떤 API 조합이 필요한가?

**최종적으로는 Codyssey 캘린더에 보이는 모든 일정을 외부 캘린더로 동기화할 수 있는지 판단할 수 있어야 한다.**

현재 단계에서는 API의 존재 여부와 동작을 검증하는 것이 우선이며, Google Calendar 연동 프로그램 구현은 조사 결과를 확인한 이후 진행한다.
