### 4. 정보 전달 의무

- [ ] 피평가자: 코드 구현 결과를 논리적으로 정당화할 수 있는가?
- [ ] 피평가자: 방법론 선택 이유를 설명할 수 있는가?
- [ ] 피평가자: "AI가那样했다"는 선택지는 없었는가?
- [ ] 평가자: 테스터기만으로 평가를 진행하지 않았는가?
- [ ] 평가자: 피평가자를 설득하고 지식을 효과적으로 전달한가?
- [ ] 평가자: "그렇게 했다", "원래 같다" 같은 무성의한 설명은 없었는가?

### 5. 피드백 작성 가이드

- [ ] 확인한 기능과 코드를 구체적으로 기술
- [ ] 평가를 통해 본 사람이 배운 점을 기록
- [ ] 문제가 있었으면 함께 해결한 과정을 서술
- [ ] Yes/No 판정이 있는 경우 근거를 명확히 밝힘
- [ ] 피평가자에 대한 존중과 격려의 표현 포함

### 6. 피드백 체계

- [ ] 객관적으로 작성하여 다른 동료들이 참고할 수 있도록 양질의 코멘트 남기기

- [ ] 완성 기준을 하나씩 직접 해 봤는가?
- [ ] 회사가 다른 AI에 같은 기획서를 줘서 영화_B_초안.html을 만들었는가?
- [ ] 두 파일에 같은 행동을 해 보고 하나를 선택했는가?
- [ ] 기획서와 다른 부분이 있었다면 본 대로 말해서 고쳤는가?
- [ ] 고쳤다면 수정본을 초안과 다른 이름으로 저장하고 해결됐는지 확인했는가?

## 동료 평가 코멘트 (예시)

### good feedback example:
> "list 시간 역순 출력 및 dictionary 출력, .json 파일 출력을 확인하였습니다. 코드 리뷰 도중 같은 내용의 코드가 main()과 validate_log() 함수에 중복 사용된 것을 발견하고, 코드 재사용성을 높일 수 있는 방안을 함께 토의했습니다."

> "6개의 인자가 들어올 때 무한 반복하는 문제가 있었고, 함께 원인을 찾았습니다. 탈출 조건 누락이 원인이었으며, 코드를 함께 파악하고 해결할 수 있는 좋은 경험이었습니다."

### feedback to avoid:
> "모든 기능이 정상 작동했습니다." → 구체성 없음
> "코드가 깔끔하고 인상 깊었습니다." → 근거 없는 칭찬
> "이 부분은 잘못 구현되었습니다." → 일방적 지적, 함께 해결하려는 시도 없음
> "Awesome", "Good!!", "수고하셨습니다!" → 무성의

## 대학원 학위논문심사원 참고사항

- 평가 결과는 객관적 근거에 기반해야 함
- 기술적 완성도보다는 학습 과정과 사고 과정의 성장을 중시
- 피드백은 constructive且 professional 해야 함
- 코드의 What(무엇을) 뿐 아니라 Why(왜 그렇게 했는지)를 함께 논의하는 것이 핵심
- 평가자와 피평가자가 함께 성장할 수 있는 학습의 장으로서의 역할을 잊지 말 것
